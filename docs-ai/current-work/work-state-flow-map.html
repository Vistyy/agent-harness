Five-Step Core Flow

The workflow should feel like one loop. Large-branch audits, slice admission, reviewer reconstruction, and closeout disposition are embedded rules, not standalone ceremonies.

Probe

  • Every non-trivial task starts by checking owner, lifecycle, nearby peers, proof risk, and failure mode.
  • Large change is just probe-plus: mechanical diff inventory, owner clusters, risk ranking.

Shape

  • Define expected finished repo state before implementation.
  • Prefer delete, collapse, reuse, rewrite, and unification before adding structure.

Slice

  • Use atomic claims, not folders, tests, docs, or prompt-sized chunks.
  • Every required claim stays visible until completed, blocked, or user-reduced.

Work State Artifacts

Work state is memory and coordination. It is not authority. The binding objective, repo reality, owner docs, proof, and reviewer judgments outrank notes.

Delivery Map

  • Queue view only: what is active, ready, waiting, or deferred.
  • Does not encode implementation authority or completion claims.

Queued Item

  • Minimum: queue_state, problem, suspected owner, next discovery move.
  • Add rank, dependency, wake-up condition, or why-not-now only when useful.
  • Use states: ready, waiting, deferred.

Active Control Sheet

  • One live objective, target state, current model, required claims, blockers, proof/review state, and links.
  • Deep reasoning goes to detail notes only when the sheet would stop being readable.
The active sheet should answer "where are we and what remains?" It should not become an investigation diary or a rigid template that rewards filling fields instead of thinking.

Core Rules Inside The Flow

Atomic Claim Rule

  • Shape: For owner X, behavior/state Y changes from current to target through lifecycle Z, proved by P.
  • Include every changed path needed for that claim and nothing that belongs to a separate claim.
  • Split on independent owners, triggers, failure policies, proofs, or cleanup dispositions.

Unification Fix-Now Rule

  • Fix now when current work exposes inconsistency and applying an established peer pattern makes the touched system simpler or more unified.
  • Queue when the change adds capability, introduces new abstraction, expands product scope, or requires a broad migration decision.
  • Every material finding still needs a disposition; "noticed" is not a final state.

Replan Trigger

  • Stop implementation when evidence changes owner, target shape, proof, slice order, or current-scope boundary.
  • Do not polish a stale plan into passing checks.

Example-Derived Lessons

  • A domain label can still be too broad; split by falsifiable claims.
  • Review-only claims are valid when they block wrong implementation.
  • Models-only, tests-only, or docs-only slices are invalid unless tied to a real owner claim.

Scope Guard

  • Fix-now is not permission to absorb every adjacent cleanup.
  • It applies to simplification or unification of the touched owner path or a peer boundary the current claim already crosses.

Reviewer Validation

Reviewers do not validate the parent story. They reconstruct enough context from repo evidence to decide whether the objective, shape, slices, proof, and cleanup converge.

Planning Critic

  • Reconstruct objective, target state, owner model, and atomic slice boundaries.
  • Block if the proposed plan narrows the objective, misses a current-scope claim, or overcomplicates shape.

Quality Guard

  • Reconstruct the assigned atomic claim and enough lifecycle context to judge the implementation.
  • Block if implementation evidence invalidates the accepted plan or simpler owner-correct shape exists.

Final Reviewer

  • Reconstruct whole objective coverage from completed claims, proof, residuals, repo state, and artifact disposition.
  • Approve only when convergence, proof, cleanup, and residual work all match the final claim.
Material divergence means BLOCK. Missing authority means BLOCKED. Test-pass, diff-only, and plan-compliance approvals are invalid for non-trivial work.

Minimum CLI Surface

The CLI exists only where mechanical checks are reliable. It speeds the agent up by handling inventory and structure, not by judging architecture.

Core

  • work-state status: inventory active control sheets, queued items, backlog details, duplicate live ownership, claim/review state, queue state, and closeout text.
  • work-state check: mechanically fail missing delivery map, duplicate live ownership, invalid or missing queue state, invalid claim/review statuses, and missing claim/review state.

Deferred Idea

  • Large-change diff inventory can be considered later only if repo teams need a reusable wrapper around ordinary git facts.
  • No such command exists in this workflow today; agents should inspect diffs directly and interpret owner, scope, current debt, and claim boundaries themselves.

Rejected Automation

  • No CLI command should pretend to classify architecture, design quality, or whether debt is current scope.
  • The CLI can require a disposition; the agent and reviewers own the disposition.
